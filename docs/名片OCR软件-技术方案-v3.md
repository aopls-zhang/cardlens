# 名片 OCR 软件 · 技术方案 v3

> 变更：iOS 暂不做本地存储；不再保存名片图片；同步内容只有字段。
> 目标：空间最省、同步最快、先跑通 OCR。
> 本版取代 v2，v2 留档。
> v3.1 增补：手机图库批量导入 + 服务端待核对队列。
> v3.2 增补：多语言（识别层换 PP-OCRv6，界面简/繁/英）。

---

## 0. 先把三件事分开

你说"图片不必保存"，这里其实混着三个不同的问题，答案不一样：

| 问题 | 答案 | 理由 |
|---|---|---|
| 图片参与同步吗？ | **否** | 只同步字段，数据量从 300 MB 降到 0.5 MB |
| 图片长期保存吗？ | **否** | 不进数据库、不进备份、不进任何副本 |
| 图片在本机短暂暂存吗？ | **是，建议是** | 核对需要参照物。没有图，你凭什么判断 OCR 把"张伟"认成了"张玮"？ |

第三行是关键：**不保存 ≠ 不暂存**。图片应该是"一次核对会话的临时载体"，活几十秒到几分钟，用完即焚。

如果连暂存都不做，核对就只能"当场对着实物名片看"——人还站在你面前、名片还在手里才行。一旦走开，识别错了永远不知道。这个代价比省下的几 MB 大得多。

所以本方案的定位是：**图片只在内存和临时目录里存在，核对结束立即删除，永不入同步。**

## 1. 简化后的架构

~~~
┌────────────────────┐        ┌──────────────────────┐
│  Android / iOS     │  临时图 │      Windows         │
│  (Capacitor / PWA) │ ──────> │  OCR 服务 (RapidOCR) │
│  拍照 + 核对 + 存字段│ <────── │  字段库 + 检索 + 导出  │
└─────────┬──────────┘  字段   └──────────┬───────────┘
          │                                │
          └────── 字段级双向同步 (mDNS) ────┘
~~~

去掉的东西：图片表、内容寻址、缩略图、blob 传输协议、按需拉取策略。
保留的东西：字段级合并、HLC、墓碑、配对、自动同步。

**iOS 的定位变了，而且变好了。** 因为不再需要本地存储，PWA 的 IndexedDB 被清理这个致命问题自动消失——Safari 只当"临时表单页"用，拍完传完核对完，什么都不留。v2 里那个要你三选一的硬矛盾，在这一版直接不存在了。

## 2. 数据量测算

| 项 | v2（含图） | v3（纯字段） |
|---|---|---|
| 单条记录 | 250–450 KB | 400–900 B |
| 1000 条 | ~300 MB | ~0.6 MB |
| 首次全量同步 | 几分钟 | < 1 秒 |
| 增量 10 条 | 2–4 MB | 6–9 KB |

这就是你说的"最高效率"：**缩小约 500 倍**。同步从"需要设计的难题"退化成"顺手就能做对的事"。

## 3. 数据模型

只留 4 张表。

~~~sql
-- 设备白名单
CREATE TABLE device (
  dev_id    TEXT PRIMARY KEY,
  name      TEXT NOT NULL,
  pubkey    TEXT,
  paired_at INTEGER,
  last_sync INTEGER
);

-- 名片主表：检索投影 + 元信息
CREATE TABLE contact (
  id          TEXT PRIMARY KEY,     -- UUIDv7
  name        TEXT,
  company     TEXT,
  title       TEXT,
  dept        TEXT,
  phones      TEXT,                 -- JSON 数组
  emails      TEXT,
  addresses   TEXT,
  webs        TEXT,
  note        TEXT,
  tags        TEXT,
  search_text TEXT,                 -- 供 FTS5
  created_hlc TEXT NOT NULL,
  updated_hlc TEXT NOT NULL,
  deleted     INTEGER NOT NULL DEFAULT 0,
  deleted_hlc TEXT,
  source_dev  TEXT,                 -- 哪台设备录入
  source_kind TEXT,                 -- camera | import | manual
  ocr_engine  TEXT,                 -- rapidocr-v5 | mlkit | none
  ocr_conf    REAL,
  verified    INTEGER NOT NULL DEFAULT 0
);

-- 字段级真值：冲突合并在这里发生
CREATE TABLE contact_field (
  contact_id TEXT    NOT NULL,
  field      TEXT    NOT NULL,      -- name|company|title|dept|phone|email|address|web|note|tag
  idx        INTEGER NOT NULL DEFAULT 0,
  value      TEXT,
  conf       REAL,                  -- OCR 置信度，人工改过置 1.0
  hlc        TEXT    NOT NULL,
  dev_id     TEXT    NOT NULL,
  deleted    INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (contact_id, field, idx)
);

-- 每个对端已确认的水位
CREATE TABLE sync_state (
  dev_id    TEXT PRIMARY KEY,
  watermark TEXT NOT NULL
);
~~~

1000 张名片 ≈ 12000 行 contact_field，SQLite 处理这个量级不构成任何性能问题。字段级表不是为了性能，是为了**不丢字段**。

## 4. OCR 放哪：两条路线

### 路线 A：手机只拍照，OCR 在 Windows（推荐先做）

~~~
手机拍照 → 图临时上传(300KB, 0.2s) → Windows RapidOCR(0.5~1.5s)
        → 字段 JSON 回传 → 手机核对 → 存字段 → 双方立刻删图
~~~

- 手机端零模型体积、零集成成本
- OCR 只有一套，升级引擎全体受益
- 精度最高（桌面 CPU 能跑完整模型）
- 代价：必须连着电脑

### 路线 B：手机本地 OCR（离线兜底，后期加）

ML Kit Text Recognition v2 或 PaddleOCR mobile，约 +20~80 MB 包体，精度低一档。只在连不上电脑时启用，结果标记 ocr_engine=mlkit，核对界面提示"离线识别，请仔细核对"。

**先做 A**。理由：你的使用场景（展会、办公室）电脑基本都在场，而且 A 能让 OCR 准确率的迭代成本降到最低——改一行 Python 就全体生效，不用重新发版。

## 5. 实验 0：先摸 OCR 的底

> **结果已出**（79 张真实扫描件、136 个名片块）：OCR 不是瓶颈，姓名在切分正确时接近 100%；
> 瓶颈是拼版切分（31/136 块无效）和字段抽取（公司 80%、职位 24%）。
> 详见 数据/基准测试报告.md。

### 原始实验设计

在写任何 App 之前，先在 Windows 上跑一次真实数据：

1. 收集 30–50 张真实名片（不同材质、中英文、竖排、有 logo 的都要有）
2. 用 RapidOCR 批量识别，输出每个字段和 bbox
3. 人工标注正确答案，算**字段级准确率**：
   - 姓名、公司、职位、手机、邮箱 各自多少
   - 哪些错误是 OCR 错、哪些是"识别对了但分错字段"
4. 看错误分布决定下一步：
   - 如果姓名/电话 > 95%：直接进 W1
   - 如果 85–95%：核对 UI 要重点设计（本方案已覆盖）
   - 如果 < 85%：考虑 PaddleOCR 服务端版，或对低置信度字段调用云 OCR

这个实验的价值：**它决定你要不要在核对界面投入两周，还是三小时。** 别跳过。

（我已经在本机后台安装 rapidocr-onnxruntime，装好就能直接跑。）

## 6. 核对界面：必须在手机上当场完成

因为图不留存，核对的时机被压缩到"拍完那几十秒"。这是本方案唯一变难的地方。

竖屏布局：

~~~
┌──────────────────────┐
│  原图（可双指缩放）    │ 40%
│  当前字段 bbox 高亮    │
├──────────────────────┤
│ 姓名  [张伟      ] 🟢 │
│ 公司  [某某科技   ] 🟡 │
│ 职位  [技术总监   ] 🟡 │
│ 手机  [138...     ] 🔴 │  ← 光标默认停在这
│ 邮箱  [           ] ⚪ │
│                      │
│ [重拍]  [保存并同步]   │ 60%
└──────────────────────┘
~~~

- 点字段 → 上半部分滚动到对应 bbox 并高亮
- 红字段必须人工确认才能保存（改一个字也算确认）
- 保存 → 写库 + 触发同步 + 立即删图
- 放弃/返回 → 也立即删图
- 崩溃恢复：启动时清理超过 2 小时的孤儿临时文件

## 7. 同步协议（可以极简了）

只有字段，一页能装下几千条，所以协议退化到三个动作：

~~~
1. HELLO   {dev_id, proto, watermark}
2. PULL    {since}        -> {changes:[...], watermark}
3. PUSH    {changes}      -> {applied, conflicts, watermark}
~~~

- changes 按 hlc 升序，一次全给（1000 条也就 600 KB，不用分页）
- 幂等：(contact_id, field, idx, hlc) 作键，重复推送无副作用
- 合并规则仍是字段级 LWW，旧值进 conflict 日志
- 删除仍是墓碑，不物理删

**唯一不能省的是字段级合并和墓碑**，因为这是正确性问题，不是性能问题。

## 8. 临时图片的生命周期

~~~
拍照 → 写入 cache/capture/<uuid>.jpg
     → 上传（A 路线）
     → 核对会话持有引用
     → 保存 / 放弃 / 超时 30 分钟
     → unlink
~~~

- 目录不参与备份、不参与同步、不进任何导出
- 每次启动扫描孤儿文件并清理
- Windows 端收到图 → 处理完立即删，不落持久目录
- 可选开关"保留最近 20 张"方便重拍对比，默认关

## 8.5 图库导入与待核对队列（v3.1 增补）

场景：宴会上连收十张名片，来不及一张张打开软件。先用**系统相机**拍下来，事后批量导入。

### 流程

~~~
相册多选(20 张) → 批量上传 → sha256 查重 → 逐张 OCR
    → 进入服务端待核对队列 → 回工位逐条核对 → 写库 → 删临时图
~~~

关键点：**队列放在 Windows 服务端，不在手机上**。手机只管传，传完就可以关；回工位用电脑大屏 + 键盘核对，甚至换另一台设备继续核。这正是"来不及开软件"场景想要的。

### 重复导入防护

~~~sql
CREATE TABLE imported_photo (
  sha256     TEXT PRIMARY KEY,   -- 只存哈希，不存图
  first_seen INTEGER NOT NULL,
  contact_id TEXT,               -- 已确认的记录
  status     TEXT                -- done | pending | failed
);
~~~

32 字节一条，一万张也才 320 KB。同一张照片重复导入，上传后立刻判定 duplicate 并跳过，不会重复录入同一张名片。

### 待核对队列

~~~sql
CREATE TABLE pending_item (
  id          TEXT PRIMARY KEY,
  photo_sha256 TEXT NOT NULL,
  tmp_path    TEXT,             -- data/tmp/<sha256>.jpg，核对完 unlink
  status      TEXT,             -- queued | ocr_done | failed | done
  source      TEXT,             -- camera | gallery
  fields_json TEXT,             -- OCR 结果 + 每字段置信度 + bbox
  created_at  INTEGER,
  expires_at  INTEGER           -- 默认 24h
);
~~~

- 上限：默认 20 条 / 24 小时，超限排队或提示先清空
- 过期清理：启动时 + 每小时扫描，删文件删行
- 缩略图：核对时按需生成，不落盘（或落 data/tmp 随主图一起删）
- 用户在手机上也能核对（同一队列，Web 页面），但在电脑上更快

### 权限：别申请敏感权限

- **Android 13+**：用系统 Photo Picker（PickVisualMedia），**不需要 READ_MEDIA_IMAGES**，合规上省一大截
- **Android 12 及以下**：action open document，同样不需要读全库
- **iOS PWA**：input type=file multiple，走系统相册选择器，零权限
- **Capacitor**：@capacitor/camera 的 pickImages，同样走系统选择器

一句话：**永远不要申请"读取整个相册"**。用户选几张就只碰那几张。

### 质量差异要处理

系统相机拍的照片没有实时取景引导，常见问题：倾斜、反光、离太远。所以批量导入的图要走同一套预处理（透视校正 + 裁剪），并且**按 OCR 置信度排序队列**——低置信度的排前面先核，别让用户核到最后才发现前面全要重录。

## 9. 里程碑（OCR 优先重排）

| 阶段 | 交付 | 验收 |
|---|---|---|
| **W0（半天）** | OCR 摸底实验 + 准确率报告 | 拿到真实名片的字段级准确率数字 |
| W1 | Windows OCR 服务：POST 图片 → 返回字段 JSON | curl 能跑通，单张 < 2s |
| W2 | Android 拍照 + 上传 + 核对 UI + 写库 | 手机上完整录入一张名片 |
| W3 | 字段同步引擎 + 收敛测试 | 两台设备随机并发编辑后一致 |
| W4 | Windows 桌面端：检索 / 导出 / 设备管理 | 1000 条不卡 |
| W5 | 配对二维码 + mDNS 自动发现 | 扫码即连 |
| W6 | iOS PWA 采集页（不存本地） | Safari 拍完传完即走 |

W2 是体验验证点，W3 是正确性验证点。W0 决定这两步的投入比例。

## 12. 多语言支持（v3.2）

### 12.1 三个层面，别混为一谈

| 层面 | 内容 | 现状 |
|---|---|---|
| 界面语言 | 按钮、字段名、提示语 | 简 / 繁 / 英 三套 |
| 识别语言 | 名片上的字认不认得 | PP-OCRv6，实测覆盖 中简 / 中繁 / 英 / 法 / 西 |
| 抽取规则 | 把文本块归位成姓名/公司/电话 | 繁简归一 + 多语关键词 + 国际号码 |

### 12.2 引擎必须换，这是硬结论

同一张繁体名片，两个模型的实测结果：

| 字段 | PP-OCRv3（旧） | PP-OCRv6（新） |
|---|---|---|
| 姓名 | 陳美玲 → **美玲**（丢字） | 陳美玲 ✅ 0.9998 |
| 职位 | 業務總監 → **整行丢失** | 業務總監 ✅ 1.0000 |
| 公司 | 臺灣雲**啟**科技 → 啟丢失 | 臺灣雲啟科技股份有限公司 ✅ |
| 地址 | 信義區 → **信羲晶** | 臺北市信義區松高路 1 號 ✅ |
| 西文 | José María → José Maria（变音丢失） | José María García ✅ |
| 西文 | Móvil → **M6vil** | Móvil ✅ |

结论：多语言不是"加一张词典"，是"换模型"。PP-OCRv3 的 ch 模型对繁体基本不可用，靠后处理补不回来（丢字无法还原）。

选型：rapidocr 3.10 内置 PP-OCRv6，同一模型同时覆盖简繁和拉丁语系，不需要按语种路由多套模型——这比"检测语种→切模型"简单得多，也更不容易在混排名片上翻车。

### 12.3 抽取层改了三处

1. **繁简归一**：用 zhconv 把文本转成简体后再匹配关键词，原文保留（显示和存储仍是繁体）。否则每套关键词都要维护两份。
2. **关键词表扩到多语**：公司后缀加了 SARL / S.L. / Inc / Associés / Asociados，职位词加了 Directeur / Gerente / Director，地址特征词加了 rue / calle / street。
3. **电话规则重写**：原来写死中国手机号 `1[3-9]\d{9}`，法西号码直接漏。改成"7–15 位数字 + 容忍空格横线括号"，+33 / +34 / +1 全部能抓。
4. **姓名规则换了逻辑**：原来是"2–4 个汉字的短文本"，抓不到 Jean-Pierre Dupont / José María García。改成"字号最大的、且不是公司行也不是职位行的那一块"——名片上姓名字号最大是跨语言的通用规律。

### 12.4 界面

- 三套文案（zh-CN / zh-TW / en），右上角按钮循环切换，localStorage 记忆
- 默认跟随 navigator.language（zh-TW/zh-HK → 繁体）
- URL 参数 ?lang=zh|tw|en 可强制覆盖，方便分享和截图

### 12.5 还没做

- 法/西地址格式差异（法国门牌在街名前、西班牙邮编在前），目前靠整行原样保留，不做结构化拆分
- 西语双姓（García López）不做姓/名拆分
- 日文、韩文、德文：PP-OCRv6 本身支持，补关键词表即可，工作量约半天
- 同一张名片正反面合并成一条记录

## 10. 取舍与风险

1. **没有原图 = 不可追溯。** 事后发现错字，无法回查是哪张名片、也无法用更好的引擎重跑。如果将来要做企业版或审计场景，这是硬伤，需要重新引入"保图"开关（可以设计成默认关、按需开，数据结构预留 image_ref 字段占位）。
2. **核对被压缩到当场。** 用户必须站着把名片核完。如果一次收到 20 张名片，现场核对会很累——可以考虑"暂存 20 张、回工位前批量核对"，但那就得临时留图，和"不存图"冲突。
3. **必须连着电脑**（路线 A）。展会现场如果只有手机，就录不了。
4. **iOS 仍是网页**：Safari 拍照走 input capture，无法做实时取景引导和四角检测，体验弱于原生。可接受，因为 iOS 本来就排后面。

第 2 点是本版最值得再想一遍的地方：**"不存图"和"现场核对"是绑在一起的**。如果用户经常一次收到一叠名片，建议允许"暂存待核对队列（最多 N 张 / 24 小时）"，这是"不长期保存"和"可核对"的折中。
